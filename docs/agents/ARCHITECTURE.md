# Architecture

One plugin — `dev-flow` — a workflow orchestrator driving a feat or fix end-to-end in Claude Code and Codex. No app code: every file is Markdown for AI agents. `CLAUDE.md` is a symlink to `AGENTS.md`.

## Plugin layout

Single-plugin repo: the repo root **is** the plugin root (official plugin-structure spec; same shape as obra/superpowers). Components live at the top level; host manifests in per-harness dot-dirs:

- `.claude-plugin/plugin.json` — Claude Code metadata (version `0.3.2`, fully self-contained — no peer dependencies).
- `.codex-plugin/plugin.json` — portable Codex plugin identity and metadata; its `"skills": "./skills/"` pointer packages the shared skills.
- `.agents/plugins/marketplace.json` — repo-local Codex marketplace; its `"./"` source points at the repo root (the plugin root).
- `commands/` — Claude slash commands (YAML `description` + body, `$ARGUMENTS`): `new-feature.md` (`/new-feature`, the orchestrator), `new-idea.md` (`/new-idea`), `bootstrap.md` (`/bootstrap`, one-command repo setup).
- `skills/` — shared skills (YAML `name`/`description` + body), including `new-feature/` (the orchestrator — single source of the gated workflow; `commands/new-feature.md` is a thin wrapper delegating to it), `commit/`, `create-github-issue/`, `execute-tasks/`, `plan/`, `tdd/`, `test/`, `review/`, `doc-fix/`, `open-pr/`, `document-structure/`, `whats-new/`, `standardize-prose/`, `bootstrap/`, and `new-idea/`. `doc-fix` repairs known docs during build with explicit in-flow context and also remains standalone.
- `references/` — per-skill reference docs shared across skills: `model-routing.md` (the single source for Claude Code role lanes, optional per-step `reviewers`/`codex_reviewers` groups and Codex's legacy `codex_reviewer_model` and `codex_implementer_model`, dispatch shapes, validation, isolated-worker brief boundaries, and before-starting procedures — crash recovery, pre-Roles upgrade mapping — that `execute-tasks`/`test`/`review`/`plan`/`brainstorm` point at); packaged via the Codex manifest's `"references"` pointer.
- `evals/` — behavioral evals per skill, run manually with `claude plugin eval`.

## The pipeline

`/new-feature` (the command, a thin wrapper) and `$dev-flow:new-feature` (the skill) both land on `skills/new-feature/SKILL.md` — the single source — which orchestrates four phases: define (brainstorm → spec → plan → create issue), build (execute TDD and known documentation repairs), verify (test → review → required documentation-consistency checkpoint), and deliver (open/update PR → check readiness and wait for manual merge → close-out). Build invokes `doc-fix` only with explicit in-flow context; standalone `doc-fix` remains available. The define handoff reuses Step 2's current viability check for unchanged material; changed or resumed material returns through Step 2 validation. Step 8 advances only on complete matching independent `consistent` evidence or justified `N/A`. Matching drift requires confirmed repair and a full execute/test/review loop; stale identity or verification requires full verification; relevant uncommitted changes stay pending, and unresolved evidence blocks advancement. A docs-only review supplement is limited to a missing documentation judgment on matching current test/review evidence with a clean relevant worktree. Step 10 validates the open PR against required checks and test/review evidence bound to the exact repository, head SHA, base ref, and base SHA. A readiness result is `passed`, `pending`, or `needs-fix`; it is separate from Goal status. The workflow never merges and advances to `merged` only after remote confirmation. It uses the status lifecycle: `brainstorm` → `spec` → `planning` → `issue` → `execute` → `test` → `review` → `doc-fix` → `pr-review` → `merged` → `done`.

## The hard gate (backbone)

Each step reads the state file's **Goal status** on entry, refuses to run unless it matches the expected incoming status, then applies the transition timing in the skill’s gate table. Steps 4, 10, and 11 defer their transitions until their completion conditions pass; close-out keeps `merged` until the task outcome and remaining work are complete. The command delegates to that single table. A status change is **three writes in one breath**: the per-feature state file's Goal status, **and** the index row (status + timestamp), **and** the state file's `Status since` timestamp (the timing source for the session-help hooks).

## State files (source of truth)

`docs/features/.feature-states/` (gitignored, never committed):
- `<feat-name>.state.md` — per-feature: Created, Updated (local + UTC offset), Status since (timing source for session-help), Base/Target branch, Goal status, Kind, Last verification, version-bound `## Verification evidence` (test and review reports with repository/head/base identity and verdict), `## PR check` (PR identity, matching head/base, result, reason, report), Risk tier, Focused verdict, optional `Codex implementer model`, a `## Roles` block (Implementer/Tester/Reviewer lanes — the step-5 combined ask writes them; sub-skill entry read-gates stop when missing), Tasks, References (verified repository, PR number and full URL).
- `.state.md` — index (dot-prefixed, sorts to top): `Feat-name | Kind | Status | Issue | Updated | Branch`, newest first; top non-`done` row is the current run; `Issue` is `—` until step 4, then `#NN`.

Resume: read the index, jump to the step matching Goal status. At `pr-review`, recover the verified PR identity before checks; only a successful all-state lookup proving no prior PR permits first-publication re-entry. Only `done` is finished; `merged` still has close-out pending, including task outcome recording.

## Fully self-contained

`dev-flow` runs step 1 with its own `brainstorm` skill and step 3 with its own contract-first `plan` skill, gated by the plan review pass: ordinary and high-risk plans get a fresh independent reviewer; small low-risk plans (≤3 tasks, one existing behavior, shared context, no unresolved dependencies, every Risk line low) use a recorded author self-check — the pass records the classification basis, scope, which check ran, and the verdict, and a plan without the recorded pass is not approvable. Repair or scope growth past eligibility escalates back to the independent review. Reviewer routing is per-step when configured: Claude Code uses `reviewers`, Codex uses `codex_reviewers`; each step list overrides its existing selection, while omitted steps keep legacy precedence. Each list member gets an independent report, all must clear, and a changed review reruns the complete affected group. Codex falls back to `codex_reviewer_model`, then the session default. Codex native implementation (`session`) can separately read the confirmed top-level `codex_implementer_model` choice; explicit inline and CLI lanes retain their current behavior. A missing native setting uses the session default; an invalid or unavailable setting blocks without fallback. The saved `Codex implementer model` state field keeps the confirmed run choice across resume. The step-5 combined Roles ask also confirms the Implementer context pick (`shared` / `per-task` / `not-used`, recorded in its own state field; legacy subagent runs read per-task): `shared` carries one worker across the task loop with delta-only follow-up briefs after a host capability check, `per-task` keeps the fresh-worker default, and a lost/overgrown worker stops with preserved evidence and explicit user choices. Implementer briefs carry a bounded goal, necessary context, boundaries, constraints, observable acceptance, and stop conditions. A confirmed coordinator diagnosis can revise one brief for the same worker; the execution note/report preserves issue identity and the used attempt across resume, while unavailable models/tools or quota/identity/permission errors stop BLOCKED without substitution. The TDD loop is dev-flow's own `tdd` skill, invoked by `execute-tasks` per task (step 5). The workflow applies context reuse: load only current-step guidance, reuse unchanged guidance, and give isolated workers bounded briefs. No step invokes another plugin's skills; `plugin.json` declares no peer dependencies. Files under `docs/features/` (never `docs/superpowers/`), specs/plans/state never committed, step order governed solely by the hard gate. The standalone skills (`document-structure`, `whats-new`, `standardize-prose`, `new-idea`) are not gated — `bootstrap` joins them: it prepares a repo for dev-flow (gitignore, gh-auth check, branch config persisted to `.dev-flow/config.json`, agent docs via `document-structure`) without ever entering the step lifecycle. `brainstorm` carries the prose-quality rule block its specs are written under, and `plan` points at it (one home); `standardize-prose` is the standalone prose-cleanup pass for existing docs, adapted in spirit from ASD-STE100 Issue 9 (owned by ASD — Aerospace, Security and Defence Industries Association of Europe; paraphrased, no STE text shipped).
